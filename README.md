# Senior Go Challenge: Partitioned Processor

Нужно реализовать конкурентный in-memory процессор событий. Он принимает события из нескольких goroutine, сохраняет порядок внутри одной партиции, параллельно обрабатывает разные партиции, повторяет временные ошибки и корректно завершает работу.

Это не задача на объём кода. Мы смотрим на границы конкурентности, линейризуемое поведение, backpressure, владение данными и lifecycle компонента.

## Сценарий

Сервис получает события от разных клиентов. `PartitionKey` определяет поток, внутри которого порядок менять нельзя. Например, два события одного заказа должны быть обработаны последовательно, а события разных заказов могут выполняться параллельно.

Публичный API уже задан в [`processor/types.go`](processor/types.go). Реализацию нужно сделать в пакете `processor`. Сигнатуры экспортированных сущностей менять нельзя; добавлять приватные типы, файлы и тесты можно.

## Требования

### 1. Приём и backpressure

- `Submit` безопасен для одновременного вызова из нескольких goroutine.
- Событие с пустым `ID` или `PartitionKey` отклоняется с `ErrInvalidEvent`.
- `QueueCapacity` ограничивает число уникальных принятых, но ещё не завершённых событий, включая событие в обработчике.
- При заполненной очереди `Submit` ждёт свободное место и возвращает `ctx.Err()`, если контекст завершился раньше.
- После начала `Close` новые события отклоняются с `ErrClosed`.
- После успешного `Submit` процессор владеет собственной копией `Payload`: последующее изменение исходного `[]byte` не должно влиять на обработчик и создавать data race.

### 2. Порядок и параллелизм

- Для одинакового `PartitionKey` обработчик вызывается строго в порядке успешного приёма событий.
- Одновременно обрабатывается не более `Workers` событий.
- События с разными ключами должны иметь возможность выполняться параллельно.
- Пока событие повторяется после ошибки, следующее событие той же партиции начинаться не может.

### 3. Повторы и ошибки

- `MaxAttempts` — общее число попыток, включая первую.
- Любая обычная ошибка обработчика повторяется до успеха или исчерпания попыток.
- Ошибка, обёрнутая `Permanent`, завершает событие без повторов.
- `Backoff(attempt)` вызывается перед повтором; `attempt` — номер уже завершившейся попытки и начинается с `1`.
- Отрицательная задержка трактуется как нулевая.

### 4. Дедупликация

- `ID` уникален в рамках жизни экземпляра процессора.
- Повторный `Submit` уже принятого `ID` возвращает `nil`, не вызывает обработчик снова и не увеличивает `Stats.Accepted`.
- Для дедупликации важен только `ID`, даже если остальные поля отличаются.

### 5. Завершение работы

- Первый вызов `Close` атомарно прекращает приём новых событий и ждёт завершения всех уже принятых событий, включая повторы.
- Несколько одновременных вызовов `Close` безопасны.
- Истечение контекста одного вызова `Close` возвращает `ctx.Err()`, но не отменяет общий drain: последующий `Close` может дождаться завершения.
- После полного drain повторный `Close` возвращает `nil`.
- Реализация не должна терять события, зависать или оставлять служебные goroutine после успешного `Close`.

### 6. Статистика

`Stats()` возвращает согласованный snapshot без data race:

- `Accepted` — число уникальных принятых событий;
- `Succeeded` — число событий, завершившихся успехом;
- `Failed` — число событий, завершившихся permanent-ошибкой или исчерпанием попыток;
- `Retried` — число дополнительных вызовов обработчика после первой попытки;
- `InFlight` — принятые события без terminal result на момент snapshot.

Для завершённого процессора выполняется `Accepted == Succeeded + Failed` и `InFlight == 0`.

## Ограничения

- Go 1.24+.
- Только стандартная библиотека.
- Нельзя создавать неограниченное число goroutine или goroutine на каждое принятое событие.
- Busy loop и polling с `time.Sleep` не допускаются.
- Публичные тесты — часть контракта, но не исчерпывают его. Решение проверяется дополнительными тестами, `go test -race` и проверкой утечек goroutine.

## Как запустить

```bash
go test ./...
go test -race ./...
go vet ./...
```

Или одной командой:

```bash
make verify
```

Стартовая реализация намеренно возвращает `ErrNotImplemented`, поэтому тесты сначала падают.
